= Managing Secrets with the External Secrets Operator on OpenShift

A hands-on workshop that teaches how to sync secrets from HashiCorp Vault into Red Hat OpenShift with the External Secrets Operator for Red Hat OpenShift. Participants install Vault and the operator, connect them with the Vault Kubernetes auth method, sync credentials into a native Kubernetes Secret, and consume and rotate those credentials in a sample application.

HashiCorp Vault serves as the example secrets store. The same approach applies to the other providers that the External Secrets Operator supports, such as AWS Secrets Manager, Azure Key Vault, and Google Secret Manager.

The workshop takes 1 to 1.5 hours and is aimed at beginner platform engineers, developers, and architects.

The content is built with Antora and published as a static site using the Red Hat Demo Platform (Showroom) UI theme.

== Workshop content

[cols="1,3"]
|===
|Page |Content

|Overview
|Why Kubernetes Secrets alone are not enough, the repository, distributor, and consumer model, and how the External Secrets Operator works

|Workshop details
|Cluster access, product versions, and the OpenShift Web Terminal

|Module 1
|Install HashiCorp Vault with Helm (development mode) and the External Secrets Operator for Red Hat OpenShift, and allow the operator to reach Vault through its egress network policy

|Module 2
|Store credentials in Vault, configure the Vault Kubernetes auth method, create a `SecretStore`, and sync a Secret with an `ExternalSecret`

|Module 3
|Deploy a sample application that reads the Secret as environment variables and as a mounted volume, rotate the password in Vault, and force an immediate sync

|Conclusion
|Key takeaways, next steps, and references
|===

== Local development

=== Preview with Antora viewer (recommended)

To preview the workshop content locally, run the Antora viewer container:

[source,sh]
----
podman run --rm --name antora -v $PWD:/antora -p 8080:8080 -i -t ghcr.io/juliaaano/antora-viewer
----

For SELinux environments, append `:z` to the volume mount:

[source,sh]
----
podman run --rm --name antora -v $PWD:/antora:z -p 8080:8080 -i -t ghcr.io/juliaaano/antora-viewer
----

Then open http://localhost:8080 in your browser. When you make changes to the content, stop the container and run it again to see updates. Live-reload is not supported.

=== Build with Antora directly

Antora requires the content to be in a Git repository. Without Podman, you can build the site with Node.js:

[source,sh]
----
npx -p @antora/cli@3.1 -p @antora/site-generator@3.1 antora site.yml
----

The site is generated in the `www/` directory.

== Cluster preparation

The workshop is admin-only and uses fixed, cluster-wide names (`vault`, `external-secrets-operator`, `external-secrets`, `secrets-demo`). Each participant needs their own cluster and a user with cluster-admin privileges. Participants install Vault and the External Secrets Operator themselves during the workshop.

=== Prepare the cluster

The `prepare-cluster.sh` script automates the following:

* Checks that you are logged in with cluster-admin privileges
* Runs pre-flight checks and warns if:
** the cluster is not running OpenShift 4.22
** the External Secrets Operator for Red Hat OpenShift is not available in the operator catalog
** another (community) External Secrets Operator is installed
** resources from a previous workshop run still exist
* Installs the OpenShift Web Terminal operator
* Deploys the lab guide container from `lab-guide-app/` into the `lab-guide` project
* Prints the lab guide URL with the cluster's console and API host names

[source,sh]
----
./prepare-cluster.sh
----

To use an externally hosted lab guide, such as GitHub Pages, instead of deploying the container to the cluster, set `LAB_GUIDE_URL` first:

[source,sh]
----
export LAB_GUIDE_URL=https://mostmark.github.io/external-secrets-operator-workshop
./prepare-cluster.sh
----

The lab guide deployment uses the image `quay.io/mostmark/external-secrets-lab:latest`. Build and push it with `build-push-container.sh` before you prepare the cluster, and make sure the Quay.io repository is public, or change the image in `lab-guide-app/lab-guide-deployment.yaml`.

The workshop downloads content from `helm.releases.hashicorp.com`, `docker.io`, and `registry.access.redhat.com`. In a disconnected cluster, mirror the Vault Helm chart, the `docker.io/hashicorp/vault` image, and the `registry.access.redhat.com/ubi9/python-312` image first.

=== Clean up the cluster

The `cleanup-cluster.sh` script removes everything the workshop installs, whether or not the participant ran the optional cleanup in Module 3:

* Deletes the `secrets-demo` project
* Uninstalls the External Secrets Operator for Red Hat OpenShift, including its components, projects, and CRDs
* Uninstalls HashiCorp Vault (Helm release, cluster role binding, and the `vault` project)
* Deletes the `lab-guide` project
* Uninstalls the OpenShift Web Terminal operator

[source,sh]
----
./cleanup-cluster.sh
----

WARNING: The script deletes the External Secrets Operator CRDs, which removes every `ExternalSecret` and `SecretStore` on the cluster. Only run it on a dedicated workshop cluster.

=== Build and push a container image

The `Containerfile` builds a UBI9-based container with Apache httpd that serves the pre-built workshop site on port 8080. The container runs as a non-root user and is suitable for deployment on OpenShift.

To build the site content first, run the Antora viewer or the `npx` build as described above, which generates output in the `www/` directory.

Then use the `build-push-container.sh` script to build a multi-architecture image (amd64 and arm64) and push it to Quay.io:

[source,sh]
----
export QUAY_USER=your-quay-username
./build-push-container.sh
----

The script builds the image as `quay.io/$QUAY_USER/external-secrets-lab:latest` and pushes it to the registry. You can then run the container locally:

[source,sh]
----
podman run --rm -p 8080:8080 quay.io/$QUAY_USER/external-secrets-lab:latest
----
